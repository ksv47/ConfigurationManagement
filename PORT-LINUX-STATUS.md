# Состояние: сборка и запуск Linux/Avalonia

Дата среза: 22.08.2026. Форк проекта `sivatorov/ConfigurationManagement`.
Всё, что относится к сборке, лежит в этой папке.

## Где мы сейчас

Linux-цель **собирается без ошибок и запускается**. Главное окно открывается,
отрисовывается, тема и иконки на месте.
Пройдено: 90 ошибок компиляции закрыты тремя группами, затем четыре дефекта,
вскрывшихся на первом исполнении.

Функциональная проверка начата и сразу упёрлась в две вещи: диалоги вешали
интерфейс намертво (исправлено), а добавление и редактирование базы
в Avalonia-ветке не реализованы вовсе, там заглушка. Подробности ниже
в разделе про функциональную проверку.

## Короткий вывод

**Ни один из 72 коммитов опубликованной истории не собирается под Linux.**
Windows/WPF-ветка у автора рабочая. Собрать проект под Linux означает доделать
порт, а не запустить сборку. Про то, запускал ли автор компилятор локально,
репозиторий ничего не говорит, и мы этого не утверждаем.

Доказательства, а не впечатление:

* В пятнадцати файлах окон (`AddEditWindow.Avalonia.cs`, `CacheCleanWindow.Avalonia.cs`,
  `SettingsWindow.Avalonia.cs` и других) не было строки `using Avalonia;`. Без неё не
  разрешается даже `Thickness`, базовый тип отступов.
* `git log -S "using Avalonia;" main -- "Configuration Management/AddEditWindow.Avalonia.cs"`
  не даёт ни одного коммита из 72. Строки в истории апстрима не было никогда.
  Ветку указывать обязательно: на `linux-port` та же команда найдёт наш коммит
  `7cc1ba3`, который эту строку и добавил.
* CI не отлавливал этого, потому что не запускался ни разу. Файлы workflow есть
  (`build.yml`, `release.yml`), но лежат в `Configuration Management/.github/workflows/`,
  а GitHub Actions читает только `.github/workflows/` в корне репозитория.
  Публичный API апстрима подтверждает: зарегистрировано 0 workflow, выполнено
  0 запусков. К тому же оба собирают только `windows-latest`, так что Linux-цель
  не проверили бы и в рабочем виде. Каталог достаточно поднять на уровень выше.

Проверить Windows-вариант на Linux не получится. Не потому, что кросс-сборки WPF
не бывает: `EnableWindowsTargeting=true` в .NET SDK её позволяет. Причина в самом
проекте: все Windows-свойства и группы элементов в csproj включены по условию
`$([MSBuild]::IsOSPlatform('Windows'))`, то есть выбираются по ОС сборки,
а не по целевому фреймворку. На Linux `net10.0-windows` вообще не попадает
в проект (`dotnet build -f net10.0-windows` даёт `NETSDK1005`), и обойти это
можно только правкой csproj, после чего сборка перестанет быть авторской.
Для Windows-варианта нужна Windows-машина с .NET 10 SDK и скрипт
`Configuration Management/build.ps1`.

## Что вскрылось на первом исполнении

Код до этого не запускался ни разу, поэтому дефекты ловились по одному.

### `7b0cde2` Два падения на старте

* `UiMetrics.AddBrushTransition` и `AddOpacityTransition` падали
  с `NullReferenceException`: `Animatable.Transitions` в Avalonia по умолчанию
  `null`, коллекцию нужно создать. Компилятор об этом предупреждал (`CS8602`),
  автор предупреждение не видел.
* `TemplateBinding` внутри шаблонов `PanelButton` и `SegmentButton` падал
  с `NotSupportedException`: у `Bind` приоритет по умолчанию `LocalValue`,
  а у выражения `TemplateBinding` приоритет `Template`, и они конфликтуют.
  Тринадцать привязок переведены на индексаторную форму
  `control[!Property] = new TemplateBinding(...)`, она берёт приоритет
  из самой привязки.

### `03aec60` Тема оформления и выход на старте

* `App.axaml` подключал только `Themes/Icons.axaml`, но не
  `Themes/LightTheme.axaml`. Из-за этого 13 ключей ресурсов, которые
  запрашивает код (`AccentBrush`, `TextPrimaryBrush`, `CardBackgroundBrush`,
  `ItemHoverBrush`, `SecondaryButton*Brush`, `TextOnAccentBrush`,
  `FavoriteBrush` и другие), не разрешались вовсе: иконки на кнопках
  оставались без `Fill` и были невидимы, акцентный фон primary-кнопок
  не применялся. Работали только семь ключей, которые случайно совпали
  с тем, что публикует `ThemeManager.ApplyColors` (ключ схемы плюс `Brush`):
  `AccentColorBrush`, `BorderColorBrush`, `ContentBackgroundColorBrush`
  и ещё четыре.
* `desktop.Shutdown` нельзя вызывать из `OnFrameworkInitializationCompleted`:
  он гасит `Dispatcher` до входа в цикл сообщений, и `MainLoop` падает
  с `InvalidOperationException`. Оба вызова относятся к этапу запуска
  (второй экземпляр и фатальная ошибка), поэтому выход делается через
  `Environment.Exit`. Проверено исполнением: запуск второго экземпляра
  при живом первом даёт код возврата 0 и пустой вывод.

### `59b8201` Синхронные диалоги вешали интерфейс

Самый тяжёлый из найденных дефектов. Эмуляция модальности была построена так:

```csharp
window.Show();
while (window.IsVisible) { Dispatcher.UIThread.RunJobs(); Thread.Sleep(10); }
```

`RunJobs` разбирает очередь задач диспетчера, но события ввода платформы
качает только `Dispatcher.MainLoop` через `PushFrame`. Поэтому после открытия
любого диалога переставали отвечать и сам диалог, и главное окно: окно уже
не могло закрыться, `IsVisible` не сбрасывался, цикл крутился вечно,
а процесс переставал реагировать на SIGTERM.

Доказано контрольным опытом. На свежем экземпляре переключатель темы меняет
фон окна с `#FFFFFF` на `#1E293B`. После вызова `ShowInfo` ни один клик и ни
одна клавиша не проходят никуда, включая сам диалог.

Исправлено в трёх местах вложенным циклом сообщений (`DispatcherFrame`
плюс `Dispatcher.PushFrame`): `ModalWindowBase.ShowDialogSync`,
`AvaloniaDialogService.ShowModalSync` и `RunSync` (файловые диалоги через
`StorageProvider` страдали тем же). При наличии владельца окно теперь
показывается через `ShowDialog(owner)`, то есть модальность настоящая,
а не имитированная.

### `d1eaa76` Новый корень кеша не отдаётся в поиск осиротевших каталогов

Находка встречного аудита, блокирующая. Добавив рабочий корень кеша,
правка выше попутно оживила режим `ClearOrphans`, который на Linux
до этого не срабатывал: корня не существовало.

Режим работает от обратного, удаляя всё, что не принадлежит базам из списка
приложения. А в `~/.1cv8/1C/1cv8` рядом с кешем баз лежат служебные каталоги
платформы: `conf` (там файлы лицензий `*.lic`, число активаций пин-кода
ограничено), `logs`, `ExtCompT`, `STT`, `standalone-server` с данными
автономного сервера. Ни один не проходит `IsVersionDirName` и ни один
не попадает в `BuildProtectedNames`, то есть все были бы удалены.

Отдельно: каталоги кеша серверных баз называются `Srvr__<сервер>__Ref__<база>__`,
а `GetCacheName` даёт только имя базы. То есть под удаление попал бы и кеш
живых баз, а фильтр по форме GUID это не решает.

У `GetCacheRoots` появился параметр `forOrphanScan`. Он затрагивает общий код
(объявление, doc-комментарий, одна точка вызова), но читается единственный раз
внутри `#if LINUX`, поэтому на Windows принимается и игнорируется. Точечная
очистка по конкретной базе новый корень использует по-прежнему.

Про размер: корень весит 9 ГБ, служебные каталоги в нём 9 МБ, то есть 0,1%.
До правки окно показывало только браузерные данные и занижало размер
на девять гигабайт, так что отображение стало точнее, а не хуже.

### Этап 5: поиск установленной платформы

`PlatformVersionService.Linux.cs` требовал, чтобы бинарники лежали в подкаталоге
`bin` каталога версии, и другого варианта не допускал. На штатной установке
их там нет: `/opt/1cv8/x86_64/8.3.27.2214/1cv8` лежит прямо в каталоге версии,
подкаталога `bin` не существует вовсе. Обе ветки перечисления версий
(каталог версии внутри корня и корень как каталог версии) отсекали такую
установку, то есть сервис не находил ни одной версии и запуск 1С на Linux
был невозможен.

Раскладка различается между дистрибутивами и версиями платформы, поэтому
предположение не заменено, а расширено: добавлен помощник `ResolveBinDirectory`,
который берёт `bin`, если бинарники там, иначе сам каталог версии. Через него
проведены семь мест, включая определение разрядности через `readelf`.
Тот же принцип, что и с путями к кешу и `ibases.v8i`: новые варианты
добавляются, прежние остаются.

Проверено исполнением. Отдельный зонд вызывает сервис из собранной сборки
через рефлексию:

* `FindInstalledVersionInfos` возвращает обе установленные версии,
  8.3.27.2214 и 8.3.27.1989;
* `ResolveVersionBinDirectory` для 8.3.27.2214 отдаёт каталог, где лежит `1cv8`.

Попутно выяснилось, что установки бывают неполные: у 8.3.27.1989 на этой машине
только тонкий клиент (`1cv8c`, `1cv8s`), а у 8.3.27.2214 полный набор
(`1cv8`, `1cv8a`, `1cv8c`, `1cv8s`, `ibcmd`, `rac`). Лаунчер это уже
учитывает: `GetBinaryNames` для тонкого клиента возвращает `1cv8c` и только
потом `1cv8`, а Конфигуратор требует `1cv8` и на такой установке честно
не найдётся. Правок не потребовалось.

Зонд лежит в скретчпаде и в репозиторий не входит.

### Этап 6 и трей: проверено исполнением

Этап 6 автор уже написал: `.desktop`-ярлыки вместо `.lnk`, `xdg-open` вместо
`explorer.exe`. Реализовывать было нечего, требовалась проверка, и она нашла
дефекты в подборе файлового менеджера, описанные ниже.

`SelectFileInManager` перебирал `nautilus`, затем `dolphin`, без оглядки
на среду, а `Process.Start` считается успехом уже при наличии бинарника
в `PATH`. Побеждал первый установленный менеджер, даже чужой для среды,
и запасные варианты не срабатывали никогда. На этой машине везло случайно:
стоит только `dolphin`.

Добавлен `LinuxDesktopEnvironment` (переменные среды, без новых
зависимостей): семейство рабочего стола, тип сессии, подбор менеджеров
с фильтром по `PATH`. Способ показа файла у менеджеров разный, и встречный
аудит поймал, что одно правило на всех неверно для половины списка:
`nemo` не понимает `--select`, у `dde-file-manager` ключ `--show-item`,
а `thunar` от пути к файлу открыл бы сам файл приложением по умолчанию,
то есть попытался бы открыть многогигабайтный `1Cv8.1CD`. Синтаксис вынесен
в таблицу, менеджер без записи в ней в перебор не попадает.

Каталог рабочего стола берётся через `xdg-user-dir DESKTOP`, и это верно:
при русской локали он `~/Рабочий стол`, а не `~/Desktop`.

**Цикл сворачивания в трей проверен и работает.** Это было последнее место
из аудитов, не покрытое исполнением. Опасение состояло в том, что `Loaded`
сработает повторно при возврате из трея, и тогда `_vm.Initialize()`
и `SetupTray()` выполнятся дважды.

Проверка на KDE Plasma, X11:

* иконка регистрируется в лотке как `org.kde.StatusNotifierItem-<pid>-0`;
* закрытие окна (`WM_DELETE_WINDOW`) размапливает окно, процесс остаётся жив,
  иконка в лотке одна;
* запуск второго экземпляра просит первый показаться и выходит с кодом 0;
* окно возвращается видимым и отрисованным;
* элемент лотка по-прежнему **один и тот же**, суффикс `-0` не сменился.

Значит `Loaded` повторно не срабатывает, дублирования нет, опасение
исполнением не подтвердилось. Ошибок приложение при этом не записало.

Не проверено: GNOME (там трей может не появиться без AppIndicator, теперь
об этом есть запись в журнале) и Wayland.

### Этап 3: заработал список баз и добавление базы

Самый крупный сдвиг. До этого центральный список не показывал ни одной базы
никогда, а добавление и редактирование были заглушками.

Четыре связанных дефекта, каждый вскрывался только после устранения предыдущего:

* **Дерево не отрисовывалось вовсе.** `LeveledTreeView` и `LeveledTreeViewItem`
  не переопределяли `StyleKeyOverride`. В Avalonia тема ищется по ключу стиля,
  для наследников `TreeView` и `TreeViewItem` её в Fluent нет, шаблон
  не находится, контрол не рисуется. Это объясняет, почему за все предыдущие
  сессии мы не видели ни одной строки. Тем же болел `PasswordBox` (три поля
  в окне настройки подключения), а `HotkeyBox` болеет до сих пор, но пока
  нигде не создаётся.
* **Селектор стиля перестал совпадать** после первой правки: он сопоставляется
  по ключу стиля, а тот теперь `TreeViewItem`.
* **Раздачи баз по узлам не было в коде.** `RebuildTree` строил только группы.
  Дописан `DistributeInfobases` по эталону WPF: разбор по пути группы
  с нормализацией разделителей, узлы «закреплённые» и «без группы».
* **Раскрытие узла не было связано с моделью.** Привязка ставится адресно
  при подготовке контейнера, а не стилем: стиль вешал бы её и на строки баз,
  у которых такого свойства нет, и журнал заполнялся бы предупреждениями.

Подключены потоки: `AddInfobase` открывает `AddEditWindow` и по выбранному типу
ведёт в `CreateInfobaseWindow`, `ConnectionSettingsWindow` или `GroupEditWindow`,
`EditInfobase` открывает настройки выбранной базы.

`ApplyFilter` переписан по эталону: и при активном фильтре, и при отключённой
группировке строится один плоский узел. Это закрыло сразу три вещи: неработавший
переключатель группировки, пустоту в режимах «Избранное» и «Недавние»
и пустоту в поиске.

Добавлен `ExportToIbasesAfterLocalChange` с предохранителями автора: работает
только при явно включённом режиме экспорта, по умолчанию `IbasesSyncMode.None`,
перед записью снимается резервная копия.

Проверено исполнением целиком: диалог выбора типа, заполнение настроек,
сохранение в `infobases.json`, отрисовка карточкой в дереве, поиск,
выделение строки. Экспорт проверялся на изолированных настройках с целью
в отдельном каталоге, контрольная сумма реального `ibases.v8i` не изменилась.

**Что поймали аудиты и чего я сам не увидел.** `EditInfobase` заменял объект
списка результатом диалога, из-за чего терялись история запусков, `SortOrder`
и номер горячей клавиши, причём с диска. В WPF-версии на этом месте стоит
комментарий, объясняющий, почему объект правится, а не заменяется.
Отключение стандартной подсветки не работало, хотя комментарий утверждал
обратное: сеттер снимал только фон покоя, а состояния Fluent задаёт вложенным
стилем на части шаблона.

Осталось незакрытым в этом узле: состояние развёрнутости не переживает
перестроение дерева (у автора хранится по ключу узла), сортировка групп
потеряна и команды сортировки пустые, узел «Без группы» стоит в конце,
а не после «Закреплённых».

### Состояние дерева, сортировка групп, порядок узлов

Три долга, названные в PR как незакрытые, закрыты.

**Свёрнутость групп** переживает перестроение дерева и перезапуск. Раньше
каждый `RebuildTree` создавал узлы заново и принудительно разворачивал их,
поэтому свёрнутые группы раскрывались после любого добавления или правки.
Состояние хранится в `AppSettings.CollapsedGroups`. Ключом служит полный путь
группы или внутренний маркер служебного узла: узлы без того и другого
не сохраняются вовсе, потому что их `NodeKey` это локализованное имя, которое
после смены языка перестало бы совпадать, а с реальной группой такого же
имени столкнулось бы.

**Сортировка групп** применяется при раскладке. Прежний `SortGroups`
сортировал узлы и тут же звал `RebuildTree`, который пересобирает всё
из `_groups` в исходном порядке, то есть был пустой операцией.

**Порядок узлов** приведён к авторскому: закреплённые, без группы, затем
группы. Раньше «без группы» стоял в конце.

`HotkeyBox` получил `StyleKeyOverride`, он болел тем же, чем дерево
и `PasswordBox`. В Linux-сборке пока не создаётся, правка на будущее.

Проверено исполнением: две группы рисуются по алфавиту, базы разложены
по ним верно, свёрнутая группа пишется в настройки и остаётся свёрнутой
после перезапуска; ввод и очистка поиска пересоздают контейнеры, после
возврата состояние не съезжает.

Аудит нашёл две вещи, обе исправлены: массовые команды писали весь файл
настроек по разу на каждый узел синхронно на потоке интерфейса, и привязка
`IsExpanded` вешалась при каждой подготовке контейнера без освобождения
прежней, а контейнеры переиспользуются.

### Панель отбора по тегам и таблица с колонками

Два шага Этапа 3, сделанные по снимкам рабочей Windows-версии.

**Теги.** Переключатель «теги» в верхней панели существовал и менял свойство,
но панели за ним не было. Ревизия достижимости команд показала, что это
не единичный случай: 8 из 28 команд вьюмодели не вызывались ни одним элементом
интерфейса. Панель сделана как у автора: подсказка видна и при пустом отборе,
чипы второй строкой, сброс справа. Состояние переключателя сохраняется.

Аудиты нашли в этом шаге четыре дефекта, все мои: утечка подписок
с квадратичным ростом (панель пересобиралась на каждый добавленный элемент
коллекции), затем утечка подписок содержимого кнопки, которую первая правка
не закрыла, сброс выбранных тегов при каждом перестроении дерева и двойная
пересборка панели.

**Колонки.** Список был карточками с текстовыми строками, у автора это таблица.
Шесть настроек видимости колонок и шесть ширин существовали и ни на что
не влияли. Заголовок и строки строятся из одного описания колонок и помещены
в общую область горизонтальной прокрутки: колонок может не хватить по ширине,
и если прокручивать только список, заголовки перестанут совпадать
со значениями.

Аудиты нашли три блокирующих: заголовок строился до загрузки настроек и потому
расходился со строками при любом недефолтном `settings.json`; колонка режима
запуска показывала сырое значение вместо локализованного; колонка сервера
для веб-базы показывала не то свойство, что в разметке автора.

**Отдельный результат аудита.** Рядом с деревом стоял авторский комментарий,
что внешний `ScrollViewer` убран, потому что отключал бы виртуализацию.
Проверка по декомпиляции Avalonia 11.3.20 показала, что у `TreeView`
виртуализации нет вовсе: панель элементов по умолчанию обычный `StackPanel`,
и ни тема Fluent, ни сам контрол её не переопределяют. Это позволило вынести
наружу и вертикальную прокрутку, иначе её ползунок при переполнении по ширине
уезжал за пределы видимой области. Комментарий переписан по факту.

Не сделано в этом шаге: изменение ширины колонок перетаскиванием, сортировка
кликом по заголовку (у автора она есть для «Название» и «Последний запуск»),
компенсация отступа уровня дерева для заголовка «Название».

## Долги, известные и осознанно не закрытые

* **Файл настроек пишут двое.** `CacheCleanWindow` сохраняет ширины колонок
  собственным циклом чтения и записи, мимо кэша вьюмодели. Следующее
  сворачивание группы перезапишет файл устаревшей копией и откатит ширины.
  Паттерн авторский, но частота записи выросла, значит вероятность
  проявления тоже. Лечится перечитыванием перед записью либо единым
  владельцем файла.
* **Мёртвые ключи в `CollapsedGroups`** от удалённых и переименованных групп
  не вычищаются. Наивная чистка потеряла бы состояние временно скрытых узлов,
  поэтому не делалась.
* **Команды сортировки не выведены в интерфейс.** `SortGroupsAscending`
  и `SortGroupsDescending` существуют во вьюмодели, но ни один элемент
  их не вызывает, поэтому смену направления проверить нечем.
* **Часть команд вьюмодели может быть так же недостижима.** Стоит отдельно
  пройтись по списку команд и сверить с интерфейсом, иначе чинится
  невидимое.
* `DeleteInfobaseWindow`, `GroupSettingsWindow`, окна ввода имени, тега
  и ссылки не подключены. `SettingsWindow` в Avalonia-версии 282 строки
  против 1554 в WPF.

встречного аудита. Под контролем версий его нет: он в `.gitignore` (коммит
`49ed93d`), и история ветки очищена от него полностью, включая коммиты,
где он был добавлен по недосмотру. Через скриншоты и логи туда попали бы
имена баз, серверов и пути подключения.

Сам список баз в репозиторий не попадает никогда: приложение хранит его
в `~/.config/ConfigurationManagement/` (`infobases.json`, `groups.json`,
`settings.json`). Каталог `publish/` закрыт вложенным
`Configuration Management/.gitignore`.

Функциональные прогоны делаются в отдельном каталоге данных через
`XDG_CONFIG_HOME`, поэтому рабочий список баз пользователя ими не затрагивается.

## Как проверялись правки

Планка сравнения бралась не по памяти, а по реальному API: reference-сборки
и XML-документация лежат локально в
`~/.nuget/packages/avalonia/11.3.20/ref/net8.0/`. Плюс встречные аудиты каждой
группы изменений двумя независимыми исполнителями. Аудит нашёл дефект
с `desktop.Shutdown`, который компилятор пропускает, и ошибку в этом документе
про `HeaderBrush`. Логи запусков, скриншоты и вердикты аудита лежат локально
в `_port/` и в репозиторий не попадают.

## Чего не покрывает компиляция

Компиляция говорит только о том, что код связывается. Всё остальное ловится
исполнением, и именно так найдены четыре дефекта первого запуска и зависание
на диалогах. Что исполнением ещё не покрыто, перечислено выше в разделе
про известные дефекты.

## Лицензия

Файла лицензии в репозитории нет ни в одном коммите. README называет проект
Open Source и ссылается на публикацию https://infostart.ru/1c/articles/2764888/,
но текста лицензии нет. Если форк выкладывается публично с нашими правками,
условия стоит уточнить у автора.

## Команды

Сборка Linux:

```bash
cd ~/project/ConfigurationManagement/"Configuration Management"
dotnet build "Configuration Management.csproj" -c Release \
  -p:RuntimeIdentifier= -p:SelfContained=false -p:PublishSingleFile=false
```

Публикация self-contained single-file после того, как сборка пройдёт:

```bash
cd ~/project/ConfigurationManagement/"Configuration Management"
./build.sh Release publish   # результат в publish/linux-x64
```

Упаковка: `package/linux/appimage.sh`, `package/linux/deb/build-deb.sh`.
