# Состояние: сборка и запуск Linux/Avalonia

Дата среза: 22.08.2026. Форк проекта `sivatorov/ConfigurationManagement`.
Всё, что относится к сборке, лежит в этой папке.

## Где мы сейчас

Linux-цель **собирается без ошибок и запускается**. Главное окно открывается,
отрисовывается, тема и иконки на месте.
Пройдено: 90 ошибок компиляции закрыты тремя группами, затем четыре дефекта,
вскрывшихся на первом исполнении.

Функциональная проверка начата и сразу упёрлась в две вещи: диалоги вешали

в разделе про функциональную проверку.

## Короткий вывод

**Ни один из 72 коммитов опубликованной истории не собирается под Linux.**
Windows/WPF-ветка у автора рабочая. Собрать проект под Linux означает доделать
порт, а не запустить сборку. Про то, запускал ли автор компилятор локально,
репозиторий ничего не говорит, и мы этого не утверждаем.

Доказательства, а не впечатление:

* В пятнадцати файлах окон (`AddEditWindow.Avalonia.cs`, `CacheCleanWindow.Avalonia.cs`,
  `SettingsWindow.Avalonia.cs` и других) не было строки `using Avalonia;`. Без неё не
  разрешается даже `Thickness`, базовый тип отступов.
* `git log -S "using Avalonia;" main -- "Configuration Management/AddEditWindow.Avalonia.cs"`
  не даёт ни одного коммита из 72. Строки в истории апстрима не было никогда.
  Ветку указывать обязательно: на `linux-port` та же команда найдёт наш коммит
  `7cc1ba3`, который эту строку и добавил.
* CI не отлавливал этого, потому что не запускался ни разу. Файлы workflow есть
  (`build.yml`, `release.yml`), но лежат в `Configuration Management/.github/workflows/`,
  а GitHub Actions читает только `.github/workflows/` в корне репозитория.
  Публичный API апстрима подтверждает: зарегистрировано 0 workflow, выполнено
  0 запусков. К тому же оба собирают только `windows-latest`, так что Linux-цель
  не проверили бы и в рабочем виде. Каталог достаточно поднять на уровень выше.

Проверить Windows-вариант на Linux не получится. Не потому, что кросс-сборки WPF
не бывает: `EnableWindowsTargeting=true` в .NET SDK её позволяет. Причина в самом
проекте: все Windows-свойства и группы элементов в csproj включены по условию
`$([MSBuild]::IsOSPlatform('Windows'))`, то есть выбираются по ОС сборки,
а не по целевому фреймворку. На Linux `net10.0-windows` вообще не попадает
в проект (`dotnet build -f net10.0-windows` даёт `NETSDK1005`), и обойти это
можно только правкой csproj, после чего сборка перестанет быть авторской.
Для Windows-варианта нужна Windows-машина с .NET 10 SDK и скрипт
`Configuration Management/build.ps1`.

## Что вскрылось на первом исполнении

Код до этого не запускался ни разу, поэтому дефекты ловились по одному.

### `7b0cde2` Два падения на старте

* `UiMetrics.AddBrushTransition` и `AddOpacityTransition` падали
  с `NullReferenceException`: `Animatable.Transitions` в Avalonia по умолчанию
  `null`, коллекцию нужно создать. Компилятор об этом предупреждал (`CS8602`),
  автор предупреждение не видел.
* `TemplateBinding` внутри шаблонов `PanelButton` и `SegmentButton` падал
  с `NotSupportedException`: у `Bind` приоритет по умолчанию `LocalValue`,
  а у выражения `TemplateBinding` приоритет `Template`, и они конфликтуют.
  Тринадцать привязок переведены на индексаторную форму
  `control[!Property] = new TemplateBinding(...)`, она берёт приоритет
  из самой привязки.

### `03aec60` Тема оформления и выход на старте

* `App.axaml` подключал только `Themes/Icons.axaml`, но не
  `Themes/LightTheme.axaml`. Из-за этого 13 ключей ресурсов, которые
  запрашивает код (`AccentBrush`, `TextPrimaryBrush`, `CardBackgroundBrush`,
  `ItemHoverBrush`, `SecondaryButton*Brush`, `TextOnAccentBrush`,
  `FavoriteBrush` и другие), не разрешались вовсе: иконки на кнопках
  оставались без `Fill` и были невидимы, акцентный фон primary-кнопок
  не применялся. Работали только семь ключей, которые случайно совпали
  с тем, что публикует `ThemeManager.ApplyColors` (ключ схемы плюс `Brush`):
  `AccentColorBrush`, `BorderColorBrush`, `ContentBackgroundColorBrush`
  и ещё четыре.
* `desktop.Shutdown` нельзя вызывать из `OnFrameworkInitializationCompleted`:
  он гасит `Dispatcher` до входа в цикл сообщений, и `MainLoop` падает
  с `InvalidOperationException`. Оба вызова относятся к этапу запуска
  (второй экземпляр и фатальная ошибка), поэтому выход делается через
  `Environment.Exit`. Проверено исполнением: запуск второго экземпляра
  при живом первом даёт код возврата 0 и пустой вывод.

### `59b8201` Синхронные диалоги вешали интерфейс

Самый тяжёлый из найденных дефектов. Эмуляция модальности была построена так:

```csharp
window.Show();
while (window.IsVisible) { Dispatcher.UIThread.RunJobs(); Thread.Sleep(10); }
```

`RunJobs` разбирает очередь задач диспетчера, но события ввода платформы
качает только `Dispatcher.MainLoop` через `PushFrame`. Поэтому после открытия
любого диалога переставали отвечать и сам диалог, и главное окно: окно уже
не могло закрыться, `IsVisible` не сбрасывался, цикл крутился вечно,
а процесс переставал реагировать на SIGTERM.

Доказано контрольным опытом. На свежем экземпляре переключатель темы меняет
фон окна с `#FFFFFF` на `#1E293B`. После вызова `ShowInfo` ни один клик и ни
одна клавиша не проходят никуда, включая сам диалог.

Исправлено в трёх местах вложенным циклом сообщений (`DispatcherFrame`
плюс `Dispatcher.PushFrame`): `ModalWindowBase.ShowDialogSync`,
`AvaloniaDialogService.ShowModalSync` и `RunSync` (файловые диалоги через
`StorageProvider` страдали тем же). При наличии владельца окно теперь
показывается через `ShowDialog(owner)`, то есть модальность настоящая,
а не имитированная.

### `d1eaa76` Новый корень кеша не отдаётся в поиск осиротевших каталогов

Находка встречного аудита, блокирующая. Добавив рабочий корень кеша,
правка выше попутно оживила режим `ClearOrphans`, который на Linux
до этого не срабатывал: корня не существовало.

Режим работает от обратного, удаляя всё, что не принадлежит базам из списка
приложения. А в `~/.1cv8/1C/1cv8` рядом с кешем баз лежат служебные каталоги
платформы: `conf` (там файлы лицензий `*.lic`, число активаций пин-кода
ограничено), `logs`, `ExtCompT`, `STT`, `standalone-server` с данными
автономного сервера. Ни один не проходит `IsVersionDirName` и ни один
не попадает в `BuildProtectedNames`, то есть все были бы удалены.

Отдельно: каталоги кеша серверных баз называются `Srvr__<сервер>__Ref__<база>__`,
а `GetCacheName` даёт только имя базы. То есть под удаление попал бы и кеш
живых баз, а фильтр по форме GUID это не решает.

У `GetCacheRoots` появился параметр `forOrphanScan`. Он затрагивает общий код
(объявление, doc-комментарий, одна точка вызова), но читается единственный раз
внутри `#if LINUX`, поэтому на Windows принимается и игнорируется. Точечная
очистка по конкретной базе новый корень использует по-прежнему.

Про размер: корень весит 9 ГБ, служебные каталоги в нём 9 МБ, то есть 0,1%.
До правки окно показывало только браузерные данные и занижало размер
на девять гигабайт, так что отображение стало точнее, а не хуже.

### Этап 5: поиск установленной платформы

`PlatformVersionService.Linux.cs` требовал, чтобы бинарники лежали в подкаталоге
`bin` каталога версии, и другого варианта не допускал. На штатной установке
их там нет: `/opt/1cv8/x86_64/8.3.27.2214/1cv8` лежит прямо в каталоге версии,
подкаталога `bin` не существует вовсе. Обе ветки перечисления версий
(каталог версии внутри корня и корень как каталог версии) отсекали такую
установку, то есть сервис не находил ни одной версии и запуск 1С на Linux
был невозможен.

Раскладка различается между дистрибутивами и версиями платформы, поэтому
предположение не заменено, а расширено: добавлен помощник `ResolveBinDirectory`,
который берёт `bin`, если бинарники там, иначе сам каталог версии. Через него
проведены семь мест, включая определение разрядности через `readelf`.
Тот же принцип, что и с путями к кешу и `ibases.v8i`: новые варианты
добавляются, прежние остаются.

Проверено исполнением. Отдельный зонд вызывает сервис из собранной сборки
через рефлексию:

* `FindInstalledVersionInfos` возвращает обе установленные версии,
  8.3.27.2214 и 8.3.27.1989;
* `ResolveVersionBinDirectory` для 8.3.27.2214 отдаёт каталог, где лежит `1cv8`.

Попутно выяснилось, что установки бывают неполные: у 8.3.27.1989 на этой машине
только тонкий клиент (`1cv8c`, `1cv8s`), а у 8.3.27.2214 полный набор
(`1cv8`, `1cv8a`, `1cv8c`, `1cv8s`, `ibcmd`, `rac`). Лаунчер это уже
учитывает: `GetBinaryNames` для тонкого клиента возвращает `1cv8c` и только
потом `1cv8`, а Конфигуратор требует `1cv8` и на такой установке честно
не найдётся. Правок не потребовалось.

Зонд лежит в скретчпаде и в репозиторий не входит.

### Этап 6 и трей: проверено исполнением

Этап 6 автор уже написал: `.desktop`-ярлыки вместо `.lnk`, `xdg-open` вместо
`explorer.exe`. Реализовывать было нечего, требовалась проверка, и она нашла
дефекты в подборе файлового менеджера, описанные ниже.

`SelectFileInManager` перебирал `nautilus`, затем `dolphin`, без оглядки
на среду, а `Process.Start` считается успехом уже при наличии бинарника
в `PATH`. Побеждал первый установленный менеджер, даже чужой для среды,
и запасные варианты не срабатывали никогда. На этой машине везло случайно:
стоит только `dolphin`.

Добавлен `LinuxDesktopEnvironment` (переменные среды, без новых
зависимостей): семейство рабочего стола, тип сессии, подбор менеджеров
с фильтром по `PATH`. Способ показа файла у менеджеров разный, и встречный
аудит поймал, что одно правило на всех неверно для половины списка:
`nemo` не понимает `--select`, у `dde-file-manager` ключ `--show-item`,
а `thunar` от пути к файлу открыл бы сам файл приложением по умолчанию,
то есть попытался бы открыть многогигабайтный `1Cv8.1CD`. Синтаксис вынесен
в таблицу, менеджер без записи в ней в перебор не попадает.

Каталог рабочего стола берётся через `xdg-user-dir DESKTOP`, и это верно:
при русской локали он `~/Рабочий стол`, а не `~/Desktop`.

**Цикл сворачивания в трей проверен и работает.** Это было последнее место
из аудитов, не покрытое исполнением. Опасение состояло в том, что `Loaded`
сработает повторно при возврате из трея, и тогда `_vm.Initialize()`
и `SetupTray()` выполнятся дважды.

Проверка на KDE Plasma, X11:

* иконка регистрируется в лотке как `org.kde.StatusNotifierItem-<pid>-0`;
* закрытие окна (`WM_DELETE_WINDOW`) размапливает окно, процесс остаётся жив,
  иконка в лотке одна;
* запуск второго экземпляра просит первый показаться и выходит с кодом 0;
* окно возвращается видимым и отрисованным;
* элемент лотка по-прежнему **один и тот же**, суффикс `-0` не сменился.

Значит `Loaded` повторно не срабатывает, дублирования нет, опасение
исполнением не подтвердилось. Ошибок приложение при этом не записало.

Не проверено: GNOME (там трей может не появиться без AppIndicator, теперь
об этом есть запись в журнале) и Wayland.

### Этап 3: заработал список баз и добавление базы

Самый крупный сдвиг. До этого центральный список не показывал ни одной базы
никогда, а добавление и редактирование были заглушками.

Четыре связанных дефекта, каждый вскрывался только после устранения предыдущего:

* **Дерево не отрисовывалось вовсе.** `LeveledTreeView` и `LeveledTreeViewItem`
  не переопределяли `StyleKeyOverride`. В Avalonia тема ищется по ключу стиля,
  для наследников `TreeView` и `TreeViewItem` её в Fluent нет, шаблон
  не находится, контрол не рисуется. Это объясняет, почему за все предыдущие
  сессии мы не видели ни одной строки. Тем же болел `PasswordBox` (три поля
  в окне настройки подключения), а `HotkeyBox` болеет до сих пор, но пока
  нигде не создаётся.
* **Селектор стиля перестал совпадать** после первой правки: он сопоставляется
  по ключу стиля, а тот теперь `TreeViewItem`.
* **Раздачи баз по узлам не было в коде.** `RebuildTree` строил только группы.
  Дописан `DistributeInfobases` по эталону WPF: разбор по пути группы
  с нормализацией разделителей, узлы «закреплённые» и «без группы».
* **Раскрытие узла не было связано с моделью.** Привязка ставится адресно
  при подготовке контейнера, а не стилем: стиль вешал бы её и на строки баз,
  у которых такого свойства нет, и журнал заполнялся бы предупреждениями.

Подключены потоки: `AddInfobase` открывает `AddEditWindow` и по выбранному типу
ведёт в `CreateInfobaseWindow`, `ConnectionSettingsWindow` или `GroupEditWindow`,
`EditInfobase` открывает настройки выбранной базы.

`ApplyFilter` переписан по эталону: и при активном фильтре, и при отключённой
группировке строится один плоский узел. Это закрыло сразу три вещи: неработавший
переключатель группировки, пустоту в режимах «Избранное» и «Недавние»
и пустоту в поиске.

Добавлен `ExportToIbasesAfterLocalChange` с предохранителями автора: работает
только при явно включённом режиме экспорта, по умолчанию `IbasesSyncMode.None`,
перед записью снимается резервная копия.

Проверено исполнением целиком: диалог выбора типа, заполнение настроек,
сохранение в `infobases.json`, отрисовка карточкой в дереве, поиск,
выделение строки. Экспорт проверялся на изолированных настройках с целью
в отдельном каталоге, контрольная сумма реального `ibases.v8i` не изменилась.

**Что поймали аудиты и чего я сам не увидел.** `EditInfobase` заменял объект
списка результатом диалога, из-за чего терялись история запусков, `SortOrder`
и номер горячей клавиши, причём с диска. В WPF-версии на этом месте стоит
комментарий, объясняющий, почему объект правится, а не заменяется.
Отключение стандартной подсветки не работало, хотя комментарий утверждал
обратное: сеттер снимал только фон покоя, а состояния Fluent задаёт вложенным
стилем на части шаблона.

Осталось незакрытым в этом узле: состояние развёрнутости не переживает
перестроение дерева (у автора хранится по ключу узла), сортировка групп
потеряна и команды сортировки пустые, узел «Без группы» стоит в конце,
а не после «Закреплённых».

### Состояние дерева, сортировка групп, порядок узлов

Три долга, названные в PR как незакрытые, закрыты.

**Свёрнутость групп** переживает перестроение дерева и перезапуск. Раньше
каждый `RebuildTree` создавал узлы заново и принудительно разворачивал их,
поэтому свёрнутые группы раскрывались после любого добавления или правки.
Состояние хранится в `AppSettings.CollapsedGroups`. Ключом служит полный путь
группы или внутренний маркер служебного узла: узлы без того и другого
не сохраняются вовсе, потому что их `NodeKey` это локализованное имя, которое
после смены языка перестало бы совпадать, а с реальной группой такого же
имени столкнулось бы.

**Сортировка групп** применяется при раскладке. Прежний `SortGroups`
сортировал узлы и тут же звал `RebuildTree`, который пересобирает всё
из `_groups` в исходном порядке, то есть был пустой операцией.

**Порядок узлов** приведён к авторскому: закреплённые, без группы, затем
группы. Раньше «без группы» стоял в конце.

`HotkeyBox` получил `StyleKeyOverride`, он болел тем же, чем дерево
и `PasswordBox`. В Linux-сборке пока не создаётся, правка на будущее.

Проверено исполнением: две группы рисуются по алфавиту, базы разложены
по ним верно, свёрнутая группа пишется в настройки и остаётся свёрнутой
после перезапуска; ввод и очистка поиска пересоздают контейнеры, после
возврата состояние не съезжает.

Аудит нашёл две вещи, обе исправлены: массовые команды писали весь файл
настроек по разу на каждый узел синхронно на потоке интерфейса, и привязка
`IsExpanded` вешалась при каждой подготовке контейнера без освобождения
прежней, а контейнеры переиспользуются.

### Панель отбора по тегам и таблица с колонками

Два шага Этапа 3, сделанные по снимкам рабочей Windows-версии.

**Теги.** Переключатель «теги» в верхней панели существовал и менял свойство,
но панели за ним не было. Ревизия достижимости команд показала, что это
не единичный случай: 8 из 28 команд вьюмодели не вызывались ни одним элементом
интерфейса. Панель сделана как у автора: подсказка видна и при пустом отборе,
чипы второй строкой, сброс справа. Состояние переключателя сохраняется.

Аудиты нашли в этом шаге четыре дефекта, все мои: утечка подписок
с квадратичным ростом (панель пересобиралась на каждый добавленный элемент
коллекции), затем утечка подписок содержимого кнопки, которую первая правка
не закрыла, сброс выбранных тегов при каждом перестроении дерева и двойная
пересборка панели.

**Колонки.** Список был карточками с текстовыми строками, у автора это таблица.
Шесть настроек видимости колонок и шесть ширин существовали и ни на что
не влияли. Заголовок и строки строятся из одного описания колонок и помещены
в общую область горизонтальной прокрутки: колонок может не хватить по ширине,
и если прокручивать только список, заголовки перестанут совпадать
со значениями.

Аудиты нашли три блокирующих: заголовок строился до загрузки настроек и потому
расходился со строками при любом недефолтном `settings.json`; колонка режима
запуска показывала сырое значение вместо локализованного; колонка сервера
для веб-базы показывала не то свойство, что в разметке автора.

**Отдельный результат аудита.** Рядом с деревом стоял авторский комментарий,
что внешний `ScrollViewer` убран, потому что отключал бы виртуализацию.
Проверка по декомпиляции Avalonia 11.3.20 показала, что у `TreeView`
виртуализации нет вовсе: панель элементов по умолчанию обычный `StackPanel`,
и ни тема Fluent, ни сам контрол её не переопределяют. Это позволило вынести
наружу и вертикальную прокрутку, иначе её ползунок при переполнении по ширине
уезжал за пределы видимой области. Комментарий переписан по факту.

Не сделано в этом шаге: изменение ширины колонок перетаскиванием, сортировка
кликом по заголовку (у автора она есть для «Название» и «Последний запуск»),
компенсация отступа уровня дерева для заголовка «Название».

### Панель инструментов над списком, звезда и булавка, сортировка кликом

Третий шаг Этапа 3, снова по снимкам рабочей Windows-версии. Три коммита:
сама работа, правки по двум встречным аудитам, правки по третьему.

**Панель инструментов.** Заголовок таблицы стал панелью, как у автора: слева
кнопки «развернуть все», «свернуть все» и две сортировки групп, видимые только
при группировке. Четыре команды вьюмодели, до сих пор не вызываемые ни одним
элементом интерфейса, стали достижимы. Иконки развёртывания взяты из авторского
`Themes/Icons.xaml`, иконки сортировки нарисованы здесь: в WPF они приходят
из MaterialDesign, которого в Linux-сборке нет.

**Сортировка кликом.** «Название» и «Последний запуск» кликабельны, повторный
клик разворачивает направление, поле и направление хранятся в настройках.
Порядок считает `ApplyCurrentSort`: закреплённые первыми, затем выбранное поле,
имя вторым ключом. Режим «Недавние» сортируется по дате запуска, как в WPF,
а не по имени, как было в Linux-ветке.

**Звезда и булавка в строке.** Цвет иконки следит за `IsFavorite` и `IsPinned`
самой базы, поэтому обе копии закреплённой базы (в своей группе и в узле
«Закреплённые») меняют вид одновременно, а строку не нужно пересобирать.

**Выравнивание заголовка.** У строки перед именем есть колонка иконки
подключения, и такая же пустая колонка появилась в заголовке. Блок кнопок групп
лежит поверх компенсатора и пустых колонок: своей колонкой он шире отступа
строки в дереве и сдвигал бы подписи вправо от значений. Ширина компенсатора
считается по самой левой видимой строке после раскладки. Пометка булавки
в заголовке прячется, когда её место занял блок кнопок.

**Расхождение с WPF, сделанное осознанно.** Настройки `ShowFavoritesButton`
и `ShowPinnedButton` управляют и колонкой заголовка, и кнопкой строки, как
написано в их описании в `AppSettings`. В WPF они меняют только ширину колонки
заголовка, а кнопки строки от них не зависят.

**Что нашли три аудита.** Подпись «Название» стояла левее имён строк на ширину
иконки. Закрепление пересобирало дерево целиком, хотя в WPF это точечный
`UpdatePinnedSection`; после порта точечного обновления вскрылось, что счётчик
в заголовке группы был готовой строкой и не обновлялся, и что при активном
фильтре пропуск обновления оставлял устаревший `AllGroupNodes`. Подписки иконок
строки не освобождались; теперь их держит карточка строки, причём хранит способ
подписаться заново, чтобы повторное присоединение к дереву восстанавливало цвета.
Ещё одно возражение (клик по звезде якобы очищает список) не подтвердилось
ни чтением ветки `ApplyFilter`, ни прогоном.

Не сделано в этом шаге: изменение ширины колонок перетаскиванием, оно
следующим шагом ниже. Подсветка выбранной строки после пересоздания строк
узла не возвращается, подробности ниже в известных дефектах.

### Ширина колонок перетаскиванием

Последний отложенный пункт по таблице. У правого края каждой колонки
заголовка появилась зона захвата: тонкая линия по центру и широкая невидимая
полоса вокруг. Приём взят из `CacheCleanWindow.Avalonia.cs`, где он уже
работал. Ширина ведётся сразу в двух сетках, в заголовке и в каждой строке,
без пересборки дерева, а в настройки пишется один раз по отпусканию и только
через вьюмодель (`UpdateColumnWidth`), а не собственным циклом чтения
и записи файла. Колонка имени до первого перетаскивания звёздная, после
становится заданной, как в WPF через `NameColumnWidthConverter`.

Вскрылось на прогоне: имя базы лежало в горизонтальной панели и потому
получало бесконечную ширину, а при узкой колонке налезало на соседние
значения вместо обрезки многоточием. Перенесено прямо в колонку.

Аудиты нашли четыре вещи, все приняты: не обрабатывалась потеря захвата
указателя (`PointerCaptureLost`), из-за чего ширина оставалась записанной
только в память; минимум ширины области считался лишь при пересборке
заголовка, и после сужения колонки прокручиваемая область оставалась прежней;
состояние перетаскивания не различало указатели и кнопки мыши; обход всего
визуального дерева строк на каждое движение указателя заменён на список,
собранный один раз на перетаскивание.

Отдельный урок про метод проверки: первая попытка перетащить колонку версии
выглядела как дефект кода, а оказалась промахом мимо восьмипиксельной зоны
захвата. Диагностическая печать в обработчике нажатия показала, что нажатие
доходит. Прицеливаться по снимку в такой мелкой зоне ненадёжно: координаты
границ колонок надо считать по пикселям снимка, а не оценивать на глаз.

### Контекстное меню строки и горячие клавиши

Меню строки базы повторяет авторское из тех команд, что во вьюмодели есть.
Не перенесены четыре пункта: регистрация COM-коннектора (на Linux COM нет),
выгрузка в dt и cf и история запусков (нет портированных сервисов запуска),
обновление сведений о конфигурации (в Avalonia-вьюмодели только заглушка
на весь список).

Горячие клавиши: F3, F4, Ctrl+E, Ctrl+N, Alt+F, Ctrl+P, Ctrl+Shift+C
и Delete. Сочетания берутся из тех же свойств вьюмодели, что показывает
подсказка в меню.

Два урока, оба стоили прогона:

* **Delete в пустом поле поиска удалял базу.** Avalonia не считает Delete
  обработанным, когда в поле нечего удалять, событие доходило до окна
  и срабатывала привязка. У Delete теперь отдельный обработчик с проверкой
  фокуса.
* **Порядок обработки клавиш в Avalonia не такой, как в WPF.** Привязки окна
  проверяются раньше, чем клавишу получит элемент с фокусом. Наши сочетания
  с правкой текста не совпадают, но Ctrl+C и подобные в этот список класть
  нельзя: они отберут клавишу у поля ввода.

Аудит нашёл ещё две вещи. Обработчик `ContextRequested`, которым я собирался
прятать меню над группой, не вызывается вовсе: `ContextMenu` ставит событию
`Handled` раньше. Прогон это подтвердил, меню открывается и над группой,
и это совпадает с WPF, поэтому мёртвый код убран, а поведение оставлено.
Подпись `Ctrl+Shift+C` переехала с пункта «Программный кеш» на «Программный
и пользовательский»: клавиша открывает очистку обоих, и переносить авторское
расхождение подписи с действием смысла не было.

### Теги в строке базы

Под именем базы идут чипы тегов: клик по названию отбирает базы с этим тегом,
крестик убирает тег, дальше кнопка «+ тег». Добавление идёт через
`TagInputWindow`: окно было написано и ни разу не создавалось. Панель чипов
перестраивается по уведомлению самой базы, поэтому правка тегов не пересобирает
дерево, а обе строки закреплённой базы обновляются разом.

Переключатель показа тегов встал в блок кнопок над списком, а не в колонку
звезды, как у автора: блок кнопок лежит поверх пустых колонок заголовка
и накрыл бы его. Сделан тем же сегментным контролом, что и переключатели
верхней панели, потому что у Fluent в нажатом состоянии свой синий фон,
чужой для этой темы. После этого шага недостижимых команд вьюмодели
не осталось.

Аудиты нашли три вещи, все приняты. Отбор по тегу снимался, а список оставался
старым: признак «показан отобранный список» снимался уже после пересборки
набора тегов, когда тега в панели больше нет. Собственные подписки карточки
строки на кисти темы (пять на строку) жили до конца процесса и теперь
привязаны к присоединению карточки к дереву. Теги переехали во вторую строку
сетки и растянуты на все колонки, как в WPF: внутри колонки имени они тянули
бы высоту строки, а значения колонок уезжали бы к её середине.

Не переносился ввод тега прямо в строке (`AddTagInlineCommand` в WPF):
у нас добавление идёт только через диалог.

### Правая панель: сведения о подключении и текущая сессия

В блоке «Информация о подключении» не хватало трёх строк против WPF: сервер
и база, тип клиента, параметры запуска. Добавлены, состав и порядок совпадают
с авторским.

Появился блок «Текущая сессия»: режим клиента и разрядность на очередной
запуск. Вьюмодель для него была готова с самого начала, семь свойств
существовали и ни на что не влияли.

Аудиты нашли главное: блок ничего не делал. Переключатели меняли свойства,
а запуск шёл мимо них, то есть интерфейс обещал поведение, которого не было.
Теперь переопределения считаются по образцу `LaunchEnterpriseWithSessionOverrides`
из WPF и применяются к запуску Предприятия, а выбор читается из настроек
и сохраняется в том же формате, что пишет WPF-версия. Сам запуск
с переопределениями исполнением не проверялся: для этого нужна живая 1С.

Заодно акцент цветовой схемы отдан стандартным контролам Fluent через
`SystemAccentColor`: переключатели брали свой цвет оттуда и в янтарном
интерфейсе оставались синими. Светлые и тёмные оттенки считаются по светлоте
HSL, потому что Fluent использует их для состояний, а схема без ключа акцента
берёт акцент встроенной светлой.

Не переносились выпадающие стрелки у кнопок запуска: команд запуска
с параметрами, с авторизацией и от администратора в Avalonia-вьюмодели нет,
а последняя на Linux в таком виде неприменима.

### Удаление базы и группы, переход по ссылке

Удаление базы шло через простое подтверждение, хотя у автора для этого есть
отдельное окно со сведениями о базе и предложением удалить файловую базу
с диска. Окно было написано и ни разу не создавалось. Удаления группы
в Avalonia-ветке не было вовсе, хотя команда удаления в WPF начинается
именно с него. Добавлена команда «Перейти по ссылке» и кнопка рядом
со стартером; окно ввода ссылки тоже было написано и не создавалось.

`GroupSettingsWindow` не подключался намеренно: он не вызывается нигде
и в WPF, это мёртвый код обеих веток. `NameInputWindow` в WPF нужен только
окну настроек, к нему вернёмся вместе с настройками.

Аудиты нашли три вещи. Выбор группы не сообщал командам о смене доступности,
и удаление при выбранной группе оставалось неактивным: в Avalonia нет
автоматического `CommandManager`, как в WPF. Сообщение о неудачном запуске
по ссылке ссылалось на несуществующий ключ словаря. Физическое удаление
файловой базы получило две проверки: каталог по символической ссылке
не удаляется (удалилась бы ссылка, а файлы базы остались бы), и наличие
`1Cv8.1CD` перепроверяется прямо перед удалением.

Отдельным наблюдением осталось: аргументы 1С в `LaunchByLink` собираются
интерполяцией строки, и кавычка во вводе пользователя может подставить свои
ключи платформы. Границы прав это не пересекает, но переделка сборки
аргументов на список ждёт своего шага.

### Окно настроек: вкладка «Отображение»

Перенесена из WPF тремя группами: значки в строке, видимые колонки, панели.
До этого шага все эти настройки можно было менять только правкой файла.
Во вьюмодели появился `ApplyDisplaySettings`: он пишет значения разом
и сохраняет один раз, как это делает WPF по кнопке.

Попутно закрыт авторский дефект самого окна: у него не был задан контекст
данных, поэтому переключатели клиента по умолчанию и разрядности не находили
свойств вьюмодели и всегда стояли пустыми. И ряд из пяти переключателей
клиента не помещался в окно, обрезаясь справа.

Аудиты нашли четыре вещи, все приняты. Переключатель группировки в верхней
панели не следил за вьюмоделью, и после смены настройки первый клик по нему
ничего не менял. Флажок «Подробности в правой панели» сохранялся и ни на что
не влиял: панель не была с ним связана, теперь по нему прячется блок сведений
о подключении, как в WPF. Вид списка не восстанавливался при запуске, хотя
WPF хранит его признаком «только избранные», а сегменты «Все, Избранное,
Недавние» без уведомления показывали бы «Все» при восстановленном отборе.
Дерево теперь пересобирается только когда изменилось то, что на него влияет:
раньше любое нажатие OK сбрасывало выделение и прокрутку.

Осталось в этом окне: вкладки «Платформы», «ibases.v8i», «Базы», редактор
цветовых схем и переназначение клавиш.

### Окно настроек: вкладка «Платформы», правая панель, тексты

Вкладка «Платформы»: список найденных версий, дополнительные пути поиска
с выбором каталога, разрядность по умолчанию. На проверенной машине список
показывает обе установленные версии.

Две настройки были в Linux-ветке мёртвыми: дополнительные пути никуда
не передавались, а разрядность по умолчанию не доходила до запуска, потому
что `OneCLauncher.DefaultArchitecture` из настроек не выставлялся вовсе.
Аудит добавил третье: пути надо отдавать и самому сервису версий
(`SetAdditionalSearchPaths`), иначе платформа из нестандартного каталога
видна в настройках, но при запуске не находится.

Правая панель при пустом выборе показывала один значок без подписи. Теперь
там «Нет выбора» с подсказкой, при выбранной группе её значок, имя и путь,
а таблица сведений о подключении показывается только для базы.

Тексты, вводившие в заблуждение в Linux-сборке, получили отдельные ключи:
подсказка про Program Files, подсказка кнопки стартера про 1CEStart.exe
и сообщение о ненайденном 1cv8.exe при создании базы. Windows-тексты
не тронуты.

Владельцем файловых диалогов стало активное окно, а не всегда главное:
выбор каталога вызывается из модального окна настроек.

### Вкладка «Базы» и автосинхронизация с ibases.v8i

Настройки синхронизации в Linux-версии существовали только в файле, а самой
автосинхронизации не было вовсе: настройки читались лишь при выгрузке после
правки базы, а «при старте», интервал и расписание не работали, потому что
таймера не существовало. Перенесено по образцу WPF, синхронизация по таймеру
идёт молча и по пути из настроек, ручная команда в верхней панели по-прежнему
спрашивает файл.

Аудиты дали здесь самый плотный улов, и почти всё про сохранность данных.
Отсутствующий файл выдавался за успешную синхронизацию. Файл, из которого
не разобралась ни одна база, вычищал список приложения. Отказ выгрузки
отменял и загрузку. Группы, созданные импортом, не сохранялись и исчезали
после перезапуска. Выбранная база могла остаться выбранной после того, как
импорт её удалил. Время расписания разбиралось нестрого, и «25:00» проходило
как длительность. Всё это закрыто, два сценария потери баз проверены прогоном.

Не переносилась часть вкладки «Базы»: каталоги шаблонов, экспорт и импорт
списка баз, обслуживание.

### Переназначение горячих клавиш

Сочетания читались из зашитых констант, а не из настроек: файл настроек общий
с WPF-версией, и там другие значения по умолчанию (F2 на правку, F8
на избранное, Insert на добавление). Linux-версия их игнорировала. На вкладке
«Клавиши» вместо справочного списка появились поля назначения на готовом
контроле `HotkeyBox`, который был написан и ни разу не создавался.

Аудиты дали три принятые находки: удаление слушало жёстко Delete и не
переназначалось, разбор сочетания не понимал того, что порождает сам контрол
(«NumPad+», «,», одни модификаторы), и не было проверок перед сохранением.
Теперь отклоняются непонятные сочетания, отбирающие обычный ввод и буфер
обмена, и одно сочетание на два действия.

Один вердикт не принят: утверждение, что привязки главного окна перехватывают
ввод в поле назначения. Окно настроек это отдельное окно верхнего уровня,
и прогон это подтвердил: F4 в поле поймалось, 1С не запускалась.

### Окно настроек: цветовые схемы

Последняя непереносённая вкладка. Редактор повторяет WPF: выбор схемы в списке
загружает её цвета, «Применить» это предпросмотр без записи настроек, выбор
цвета меняет только схему в памяти, сохранение идёт по ОК окна. Подключился
`NameInputWindow`: он нужен для создания и переименования схемы.

Семь вкладок с русскими подписями в строку не помещаются ни при какой разумной
ширине окна, поэтому полоса вкладок переехала влево (`TabStripPlacement.Left`).

Проверено исполнением: создание, переименование, удаление с подтверждением,
выгрузка и загрузка файла схемы через портальный диалог, предпросмотр,
сохранение по ОК и его переживание перезапуска, откат при закрытии крестиком.

Аудиты дали находки, все приняты:

* редактор открывался с применённой предпросмотром схемы, а не с сохранённой,
  и после закрытия крестиком показывал непринятые цвета;
* занятое имя молча перезаписывало чужой файл схемы, хотя текст сообщения
  обещает обратное;
* переименование удаляло старый файл до записи нового: ошибка записи оставляла
  бы пользователя без обеих схем;
* файловые операции и чтение каталога схем выбрасывали исключение из
  обработчика кнопки вместо сообщения;
* в окне сообщения текст не переносился: в горизонтальной стопке он получает
  бесконечную ширину, и длинная строка обрезалась. Это чинит все сообщения
  приложения, а не только схемы.

Осознанное расхождение с WPF: проверка занятости имени. В WPF её нет, и там
создание схемы с существующим именем перезаписывает чужой файл молча. Правка
не переносится в `linux-fixes` как исправление WPF, но в Linux-ветке остаётся:
поведение хуже, чем обещает собственный текст сообщения.

### Перетаскивание баз и групп мышью

База переносится в другую группу, группа вкладывается в другую и выносится
обратно в корень сбросом на узел без группы («Закреплённые», «Без группы»).
Вьюмодель получила порты `MoveInfobaseToGroup` и `MoveGroupUnder`: в WPF они
живут в `MainViewModel.cs`, а этот файл в Linux-сборку не входит вовсе.

Перед кодом прошла разведка пятью исполнителями: три читали код (эталон WPF,
устройство списка, вьюмодель), четвёртый распаковал сборки Avalonia и читал
исходники `DragDrop`, `InProcessDragSource` и X11-бэкенда, пятый сводил факты
и искал противоречия. Что из этого важно и по документации не видно:

* под X11 в Avalonia 11.3.20 протокола XDND нет вовсе, работает внутрипроцессный
  `InProcessDragSource`. Перетаскивание из чужих приложений и наружу не заработает,
  и это граница платформы, а не недоделка порта;
* отпускание приходит на последнюю цель независимо от того, что вернул `DragOver`,
  в отличие от WPF. Поэтому обработчик `Drop` повторяет все проверки сам, иначе
  цикл в иерархии групп создавался бы одним броском;
* `TreeView` помечает `PointerPressed` обработанным, обновляя выделение, поэтому
  обычная подписка не срабатывает. Нагрузка фиксируется по туннелю
  (`RoutingStrategies.Tunnel`) — прямой аналог `PreviewMouseLeftButtonDown`;
* во время перетаскивания сырые движения помечаются обработанными, поэтому hover
  строки не работает, а курсор берётся из темы X11 по имени `dnd-move`, которого
  в теме может не быть. Своей подсветки цели пока нет, это долг ниже.

Проверено исполнением: перенос базы между группами с пересчётом порядка в целевой
группе; вложение группы вместе с подгруппами и базами (пути баз переписались,
ни одна не уехала в «Без группы»); вынос группы обратно в корень; отказ на попытку
вложить группу в саму себя и в собственного потомка; отмена по Escape без залипания
состояния; клик по звезде не начинает перетаскивание; изменение ширины колонок
работает как раньше.

Два дефекта нашёл прогон, оба закрыты:

* вложенные группы рисовались свёрнутыми независимо от модели. Раскрытие
  связывалось по событию `ContainerPrepared` у дерева, а вложенные контейнеры
  готовит родительский `TreeViewItem`, и его событие до дерева не доходит.
  Привязка переехала в `LeveledTreeView.PrepareContainerForItemOverride`, куда
  `TreeViewItem` перенаправляет подготовку своих детей. Дефект был и до
  перетаскивания, но вложенные группы в Linux-сборке были недостижимы;
* подзаголовок правой панели после переноса показывал старую группу: выбор не
  менялся, а свойство считается от базы и об изменении не узнавало.

Осознанные расхождения с WPF, оба в сторону сохранности данных:

* сброс базы на узлы «Все базы» и результат поиска запрещён. В WPF он разрешён
  и молча обнуляет группу базы, потому что путь у таких узлов считается пустым;
* `MoveGroupUnder` сохраняет переложенные ключи свёрнутости. В WPF они остаются
  только в памяти и после перезапуска свёрнутость едет по старым путям.

Чего перетаскивание не делает, и это то же самое, что в WPF: вставка между строками
пользователю не видна. `insertBefore` и `SortOrder` считаются честно, но порядок
внутри группы показывается по полю сортировки, а «SortOrder» из интерфейса не
включается ни в одной из версий: кликабельные заголовки задают только «Name»
и «LastLaunchDate». То есть перетаскивание внутри одной группы меняет только число
в `infobases.json`. Автопрокрутки к краю списка нет тоже ни там, ни там.

### Правки перетаскивания по двум встречным аудитам (`dbad665`)

Два независимых аудита коммита `2c4c4d6` дали шесть находок, четыре закрыты
правкой, две отклонены с обоснованием.

* **Сброс группы на служебный узел выносил её в корень.** Проверка допустимости
  перечисляла разрешённые узлы поимённо только для баз, а для группы разрешала
  любой узел без группы, включая «Все базы», результат поиска и «Закреплённые».
  Вернуть подгруппу на место в интерфейсе нечем: смена родителя есть только
  у перетаскивания, `GroupSettingsWindow` не открывается ниоткуда. Теперь для
  группы разрешены настоящая группа и узел «Без группы».
* **Исключение из отпускания роняло приложение целиком.** Проверено исполнением:
  сборка с намеренным броском в обработчике завершается по `Critical error`
  в главном цикле диспетчера. Стек: `DragDropDevice.ProcessRawEvent` -> `Drop`
  -> `EventRoute.RaiseEventImpl` -> обработчик, ни одного `try` по дороге.
  Аудит предсказывал залипание перетаскивания, исполнение показало падение
  процесса. Тело отпускания вынесено в `ApplyDrop` под `try`.
* **Экспорт в `ibases.v8i` шёл после неудачной записи своих файлов.** Внешний
  файл получал новую группу, свой оставался со старой, перезапуск их разводил.
  `SaveSilently` и `SaveGroupsSilently` возвращают признак успеха, экспорт идёт
  только когда записались оба файла. Проверено исполнением: каталог данных
  закрыт на запись, в журнале `UnauthorizedAccessException` на `infobases.json.tmp`,
  файла выгрузки нет; после возврата прав перенос и выгрузка прошли.
* **Сброс группы на её текущего родителя** писал три файла ради нулевого
  изменения. Добавлен ранний выход, проверено по времени изменения файлов.
* Ключ свёрнутости при переносе подветки резался по длине исходного пути, хотя
  совпадение искалось по нормализованному; при расхождении форматов ключ
  получался битым. Режется по нормализованному.
* Подзаголовок правой панели обновляется и после переноса группы. Находка верна
  по коду, но через мышь недостижима: нажатие на строку группы переносит
  выделение на неё, и выбранной базы в этот момент уже нет.

Отклонено с обоснованием:

* `PersistCollapsedGroups` в переносе группы игнорирует `_deferCollapsedSave`.
  Флаг взводится только внутри «развернуть или свернуть всё», а перенос группы
  внутри него не выполняется, игнорировать там нечего.
* Столкновение имён групп при переносе (две группы с одинаковой цепочкой имён
  сливаются, потому что путь хранится строкой). Дыра есть, но она унаследована:
  уникальность имён не проверяется нигде, включая WPF-ветку и создание группы.
  Правка вышла бы за границы порта.

Проверено исполнением по итоговой сборке: отказ при сбросе группы на
«Закреплённые», вынос группы в корень через «Без группы», вложение группы,
перенос базы между группами с пересчётом порядка.

Найдено прогоном сверх аудита: **после переноса группы теряется вся выборка,**
правая панель показывает «Нет выбора». Это не регрессия перетаскивания:
`RebuildTree` обнуляет `SelectedGroupNode` намеренно и делает это при любой
перестройке дерева. Записано в известные дефекты ниже.

Ошибка в оснастке, стоившая времени: `pkill -f "linux-x64/ConfigurationManagement"`
не убивает приложение, потому что в командной строке процесса только
`./ConfigurationManagement`. Пять экземпляров работали одновременно и
перезаписывали файлы друг друга, дерево в окне расходилось с диском.
Убивать по списку из `pgrep -af "ConfigurationManagement$"`.

### Действие после запуска базы или конфигуратора (`6ed13ea`, `42163e4`)

Настройка «что делать с окном после успешного запуска»: ничего, свернуть в трей
или закрыть в трей. Автор объявил её готовой для обеих платформ в CHANGELOG,
но в Avalonia-ветке не было ни свойства, ни события, ни элемента в настройках.

Что вскрылось попутно и касается обеих платформ:

* **Ключей локализации не было ни в одном языке.** `Translate` при отсутствии
  ключа возвращает сам ключ, поэтому окно настроек WPF показывало строки вида
  `Settings.General.AfterLaunchAction.None`. Добавлены четыре ключа в `ru.json`
  и `en.json`, это чинит и Windows-версию.
* **В Avalonia все пути запуска сходятся в одну точку** `OnLaunched`, тогда как
  в WPF уведомление расставлено в трёх местах. Проверено перечислением всех
  вызывающих: кнопки правой панели, контекстное меню, горячие клавиши, меню
  трея, недавние базы из трея, двойной клик. Отдельно добавлен переход по
  ссылке: он поднимает 1С мимо этой точки.

Два встречных аудита дали десять находок, семь закрыты правкой:

* **Семантика расходилась с эталоном.** В WPF оба пункта уводят окно в трей
  (`MinimizeToTray` делает `Hide` и сбрасывает состояние, `HideToTray` то же
  минус сброс). В первой версии порта «свернуть» означало сворачивание в панель
  задач, то есть одно значение настройки давало на двух платформах разное
  поведение, а общий файл локализации получал подпись, неверную для Windows.
  Приведено к эталону, подписи взяты по его поведению.
* **Восстановимость окна угадывалась по имени окружения.** Условие считало трей
  недоступным только на GNOME. На деле в Avalonia 11.3.20 у трея под Linux один
  бэкенд, `DBusTrayIconImpl` поверх `org.kde.StatusNotifierItem`, резервного
  XEmbed нет вовсе, поэтому значка не будет на любой сессии без
  StatusNotifier-хоста: xfce4-panel без плагина, i3, sway, LXDE. Обратный
  промах тоже был: на штатной Ubuntu GNOME трей работает, а пункт молча
  подменялся сворачиванием. Теперь считаются два пути возврата: созданный без
  ошибки значок и повторный запуск приложения через файл-сигнал, который жив,
  только пока включён режим единственного экземпляра. Нет ни одного из них,
  окно сворачивается и пишет в журнал причину.
* Пустой выбор в списке настроек оставляет прежнее значение, как в WPF,
  а не гасит настройку.
* Терминология английских подписей приведена к остальному файлу
  (`infobase` и `Configurator`).

Названо и оставлено как есть: значение настройки записывается на диск в момент
нажатия «ОК», до проверки горячих клавиш, поэтому последующая «Отмена» его уже
не отменит. Ровно так же ведут себя соседние `ApplyColorScheme`
и `ApplyPlatformSettings`, это свойство всего окна, а не этой настройки.

Проверено исполнением, обе ветки:

* KDE Plasma, единственный экземпляр: окно уходит в трей, снимается с экрана
  (`_NET_WM_STATE` пуст), возвращается повторным запуском приложения;
* подменённое окружение `XDG_CURRENT_DESKTOP=ubuntu:GNOME` с разрешёнными
  несколькими экземплярами: окно сворачивается в `_NET_WM_STATE_HIDDEN`,
  в журнале запись о причине. Эта ветка раньше не исполнялась ни разу.

Второй коммит автора (`MultiFormatConverter`) в Avalonia переносить нечего: он
обходит ограничение WPF, где `MultiBinding StringFormat` не работает для
`ToolTip`, а здесь разметка кодовая и подсказки задаются строкой.

## Проверки с настоящей 1С

Появились рабочие базы, и часть долга «ничего не проверялось на реальной
платформе» закрыта. Базы лежат вне репозитория, команды их создания
и учётные данные СУБД описаны в `_port/harness/README.md`.

Проверено на платформе 8.3.27.2214:

* файловая база: запуск Предприятия (`1cv8 ENTERPRISE /F <путь>`) открывает
  окно конфигурации, запуск Конфигуратора (`DESIGNER /F`) открывает
  конфигуратор;
* клиент-серверная база в существующем кластере на PostgreSQL 16:
  запуск Предприятия (`ENTERPRISE /S localhost\cm_proba_cs`) открывает базу;
* тип базы приложение определяет верно, файловая и клиент-серверная строки
  различаются иконкой и подписью.

**Определение версии конфигурации никуда не годится, и это выяснилось на живой
базе.** `ConfigurationInfoService` сначала пробует COM-коннектор (под Linux его
нет), а затем эвристику: читает первые 4 МБ файла `1Cv8.1CD` и ищет строку вида
`N.N.N.N`. Проверено на двух базах: пустая отдаёт версию платформы
`8.3.27.2214` вместо версии конфигурации, а база с честно заданной версией
`1.2.3.4` не отдаёт ничего, потому что строки в этих мегабайтах нет. Пока это
не проявляется: в Avalonia-ветке служба не вызывается вовсе, колонка
«Конфигурация» не заполняется. При переносе эвристику брать нельзя.

Замена найдена и проверена на живых базах, для файловых она быстрая и точная:

```bash
ibcmd infobase config export --db-path=<каталог базы> objects --out=<каталог> Configuration
```

Выгружается только корень конфигурации, полтора-два секунды на пустой базе.
В `Configuration.xml` лежат `<Name>`, `<Vendor>` и `<Version>`: на базе
с версией `1.2.3.4` отдаёт именно её, на пустой отдаёт пустой `<Version/>`,
а не версию платформы. Имя конфигурации эвристика не давала вообще, здесь оно
есть. Лицензия для `ibcmd` не нужна, окно не открывается.

Для клиент-серверных баз этот путь не подходит: `ibcmd` подключается к СУБД
напрямую (`--dbms`, `--db-server`, `--db-user`, `--db-pwd`), а этих
учётных данных у приложения нет, оно знает только кластер. Там нужен запуск
конфигуратора под пользователем базы, как в известных реализациях, и это
надо будет замерить: у выгрузки конфигуратора нет фильтра по корню, то есть
на большой конфигурации она будет долгой.

## Долги, известные и осознанно не закрытые

* **Файл настроек пишут двое.** `CacheCleanWindow` сохраняет ширины колонок
  собственным циклом чтения и записи, мимо кэша вьюмодели. Следующее
  сворачивание группы перезапишет файл устаревшей копией и откатит ширины.
  Паттерн авторский, но частота записи выросла, значит вероятность
  проявления тоже. Лечится перечитыванием перед записью либо единым
  владельцем файла.
* **Разрядность по умолчанию хранится статически** в `OneCLauncher`. При одном
  окне приложения это работает верно, но два экземпляра вьюмодели переписали бы
  значение друг другу. Отдельного владельца настройки заводить не стали.
* **Синхронизация идёт в потоке интерфейса.** Таймер Avalonia работает
  на диспетчере, а выгрузка, загрузка и пересборка дерева синхронные: на
  медленном или сетевом файле окно подвиснет. В WPF так же, перенос в фон
  это отдельный шаг со своими рисками по коллекциям.
* **Ошибки записи файлов молчат.** `SaveSilently` и `SaveSettingsSilently`
  пишут исключение в журнал и ничего не говорят пользователю, тогда как
  WPF-версия показывает ошибку диалогом. Это общий приём всей Avalonia-ветки
  (закрепление, избранное, теги, удаление), а не отдельного места, поэтому
  лечится разом, а не по одному вызову.
* **Мёртвые ключи в `CollapsedGroups`** от удалённых и переименованных групп
  не вычищаются. Наивная чистка потеряла бы состояние временно скрытых узлов,
  поэтому не делалась.
* **Часть команд вьюмодели может быть так же недостижима.** Стоит отдельно
  пройтись по списку команд и сверить с интерфейсом, иначе чинится
  невидимое.
* `DeleteInfobaseWindow`, `GroupSettingsWindow` и окно ввода ссылки
  не подключены. `GroupSettingsWindow` мёртв и в WPF: его никто не открывает.

## Известные дефекты, ещё не закрытые

* **Подсветка выбранной строки и позиция прокрутки теряются при пересоздании
  строк.**
  Закрепление и открепление перестраивают состав узла, и дерево снимает
  выделение. Для базы сама выборка сохраняется: правая панель, строка состояния
  и команды работают с прежней базой. **Для группы не сохраняется ничего:**
  `RebuildTree` обнуляет `SelectedGroupNode` намеренно, потому что узлы
  пересоздаются и прежний узел больше не тот, что показан в дереве. После
  переноса группы правая панель показывает «Нет выбора». Лечится не в
  перетаскивании, а в `RebuildTree`: восстанавливать выбор по идентификатору
  группы, а не по ссылке на узел. Пробовались три способа вернуть
  подсветку (`SelectedItem` у дерева, `IsSelected` у контейнера, отложенная
  переустановка), ни один не удержался. Поведение то же, что было раньше,
  когда закрепление пересобирало дерево целиком.
* **Подписки на ресурсы темы без отписки** в остальных местах (правая панель,
  диалоги, верхняя панель). `ThemeBrushes.Bind` и
  `IconHelper.MakeIcon` вызывают `GetResourceObservable(...).Subscribe(...)`
  и выбрасывают возвращённый `IDisposable`. В строках списка это закрыто:
  подписки держит карточка строки. Наблюдатель держит сильную ссылку
  на контрол, а observable живёт у `Application.Current`. Для главного окна
  безвредно, но каждый показ диалога навсегда укореняет его визуальное дерево.
  Авторское, диффом не вводилось.
* **Смена языка не перерисовывает подписи.** Весь Avalonia-интерфейс строит
  тексты один раз через `LocalizationManager.T`, без привязки и без подписки
  на смену языка, поэтому подписи меняются только после пересборки окна
  (её делает переключатель компактного режима). Дефект не нового меню,
  а всего окна.
* **Окна сообщений не оформлены темой.** `MessageWindow` в
  `AvaloniaDialogService` строит содержимое без кистей темы, поэтому выглядит
  как обычное окно Fluent на белом фоне, в отрыве от остального интерфейса.
* **Сегмент «Все»** в верхней панели: акцентная подложка уже текста,
  надпись частично перекрыта.
* **У перетаскивания нет подсветки цели.** Пользователь видит только курсор
  темы X11 (`dnd-move`), которого в теме может не быть, а штатная подсветка
  строки под указателем во время перетаскивания не работает: Avalonia помечает
  сырые движения обработанными. В WPF подсветки нет тоже, но там курсор
  системный и всегда есть.
* **Не проверялось ничего, что требует реальной 1С:** запуск Предприятия
  и Конфигуратора, очистка кеша, синхронизация с `ibases.v8i`, определение
  версий платформы.

## Приватность артефактов

Каталог `_port/` держит логи запуска, скриншоты приложения и материалы
встречного аудита. Под контролем версий его нет: он в `.gitignore` (коммит
`49ed93d`), и история ветки очищена от него полностью, включая коммиты,
где он был добавлен по недосмотру. Через скриншоты и логи туда попали бы
имена баз, серверов и пути подключения.

Сам список баз в репозиторий не попадает никогда: приложение хранит его
в `~/.config/ConfigurationManagement/` (`infobases.json`, `groups.json`,
`settings.json`). Каталог `publish/` закрыт вложенным
`Configuration Management/.gitignore`.

Функциональные прогоны делаются в отдельном каталоге данных через
`XDG_CONFIG_HOME`, поэтому рабочий список баз пользователя ими не затрагивается.

## Как проверялись правки

Планка сравнения бралась не по памяти, а по реальному API: reference-сборки
и XML-документация лежат локально в
`~/.nuget/packages/avalonia/11.3.20/ref/net8.0/`. Плюс встречные аудиты каждой
группы изменений двумя независимыми исполнителями. Аудит нашёл дефект
с `desktop.Shutdown`, который компилятор пропускает, и ошибку в этом документе
про `HeaderBrush`. Логи запусков, скриншоты и вердикты аудита лежат локально
в `_port/` и в репозиторий не попадают.

## Чего не покрывает компиляция

Компиляция говорит только о том, что код связывается. Всё остальное ловится
исполнением, и именно так найдены четыре дефекта первого запуска и зависание
на диалогах. Что исполнением ещё не покрыто, перечислено выше в разделе
про известные дефекты.

## Лицензия

Файла лицензии в репозитории нет ни в одном коммите. README называет проект
Open Source и ссылается на публикацию https://infostart.ru/1c/articles/2764888/,
но текста лицензии нет. Если форк выкладывается публично с нашими правками,
условия стоит уточнить у автора.

## Команды

Сборка Linux:

```bash
cd ~/project/ConfigurationManagement/"Configuration Management"
dotnet build "Configuration Management.csproj" -c Release \
  -p:RuntimeIdentifier= -p:SelfContained=false -p:PublishSingleFile=false
```

Публикация self-contained single-file после того, как сборка пройдёт:

```bash
cd ~/project/ConfigurationManagement/"Configuration Management"
./build.sh Release publish   # результат в publish/linux-x64
```

Упаковка: `package/linux/appimage.sh`, `package/linux/deb/build-deb.sh`.
